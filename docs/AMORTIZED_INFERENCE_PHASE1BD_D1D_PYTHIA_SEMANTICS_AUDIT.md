# Phase 1B-D1D-A static evidence-framework hardening report

## Completion status and fixed boundary

This phase-scoped change hardens the static PYTHIA source-evidence framework.
It does not execute PYTHIA, APFEL, LHAPDF, a repository physics binary,
`Pythia::init()`, or `Pythia::next()`. It creates no events or datasets,
performs no observable scan or numerical physics work, selects no architecture,
authorizes no prototype, and does no D2 work.

The preserved scientific decisions are:

```text
D1C_FINAL_DECISION = FAIL
MINIMAL_PUBLIC_READER_PATCH = INSUFFICIENT
D1D_A_RESULT = EVIDENCE_CORRECTION_REQUIRED
```

Issue #10 and D2 remain blocked. PR #43 remains open and draft.

## Why the v3/v2 correction was still insufficient

Audit v3 and search-manifest v2 corrected important defects in the original
evidence, but did not establish readiness:

- deriving metadata for 779 identifiers was not equivalent to searching all
  779 identifiers; P10 searched only the fixed 18-name regression subset;
- path/line suppression removed all P10 occurrences on a line already present
  in v1, including independently new identifiers on that line;
- newly added final semantic classes came primarily from identifier families;
- newly added reachability dispositions came primarily from filename strings;
- 66 denominator repairs were regenerated by broad token heuristics, including
  `wt`;
- the owning-symbol check searched a preceding 1,000-line window rather than
  proving that the coordinate was inside a function body;
- the manifest declared grep/POSIX ERE while replay used Python regex; and
- readiness contained constant `true` values and treated material recall
  closure as equivalent to resolving `getXPDF`.

The historical figures of 90 legitimate findings and 15 `getXPDF` paths are
now integrity-review baselines only. They are not forced totals.

## Authoritative search engine

Exactly one engine is authoritative:

```text
PYTHON_REGEX_OCCURRENCE_ENGINE_V1
```

Every specification records the engine identity, Python regex, `ASCII` flag,
token-extraction regex, source-inventory identity, and deterministic ordering
rule. Human-readable grep argv remain supplementary and explicitly
non-authoritative. Validation rejects an unsupported engine, flags or
pattern/engine mismatch, a stored occurrence set that differs from replay,
duplicate keys, or non-deterministic order.

The canonical occurrence key is:

```text
engine identity
specification ID
inventory file ID
line
UTF-8 byte offset
match ordinal
normalized identifier
identifier hash
```

## Machine candidates versus reviewed evidence

Machine discovery may propose semantic and reachability hints, but cannot
assign a final scientific class, materiality disposition, owning symbol, or
architecture-readiness result. The complete P10 ledger has 63,763 candidates:

| Scientific review state | Count |
|---|---:|
| `MACHINE_DISCOVERED_UNREVIEWED` | 63,674 |
| `POLICY_UNRESOLVED` | 15 |
| `SOURCE_REVIEWED_BOUNDARY` | 37 |
| `SOURCE_REVIEWED_POINTER_OR_POLICY` | 37 |
| `SOURCE_REVIEWED_MATERIAL` | 0 |
| `SOURCE_REVIEWED_NONMATERIAL` | 0 |

The v3 name/path-derived material additions were deliberately returned to
machine-unreviewed candidate status. Of the ledger, 63,689 occurrences are
material candidates or have unresolved materiality; 63,674 of those are
machine-unreviewed. The full set contains 35 unresolved `getXPDF` occurrences.
Fifteen are the preserved policy-reviewed path set and remain unclassified;
the other 20 are additional complete-vocabulary occurrences and are also not
silently classified.

`getXPDF` is not the only unresolved family. The ledger has 63,654 other
unresolved/materiality-unresolved occurrences across 778 identifier families.
The largest raw families include `state` (6,003), `size` (4,563), `id`
(3,932), `push_back` (3,198), `p` (3,130), `Vec4` (2,824), `e` (1,945),
`flavour` (1,661), `set` (1,458), and `weight` (1,356). These counts are
candidate-review workload, not claims that every occurrence is scientifically
material.

## Curated scientific evidence and function ownership

Final semantic and reachability fields for the 137 retained historical groups
and 672 concrete members are explicitly marked as source-reviewed evidence.
Identifier-family and filename functions now return only non-binding
`REVIEW_HINT_*` values, which are outside the final semantic/reachability
enums.

All 66 prior denominator corrections are stored in an explicit curated table.
Each entry has a source file and line, owning expression or paraphrase,
mathematical role, direct-source status, final disposition, and rationale:

```text
expected members          = 66
curated dispositions      = 66
unresolved members        = 0
result                    = COMPLETE
```

Function ownership is established by masking comments and string/character
literals, identifying qualified function definitions, and brace-tracking each
body. A final-evidence coordinate must lie inside the matching range:

```text
confirmed final evidence coordinates     = 672
invalid or unresolved owning symbols      = 0
result                                    = PASS
```

An unresolvable candidate is recorded as `OWNING_SYMBOL_UNRESOLVED`; it is not
silently accepted as final evidence.

| zero unresolved material candidates | `false` |

Consequently, readiness is derived as:

```text

```

It is not hardcoded. `READY_FOR_ARCHITECTURE_COMPARISON` cannot be reached
while any condition is false.

## Unresolved limitations and one next step

Static discovery does not decide materiality, semantic role, reachability, or
architecture suitability for 63,674 machine-unreviewed candidates. The 35
unresolved `getXPDF` occurrences remain within that broader closure problem.
Runtime PDF-pointer identity and alpha_s routing remain explicitly deferred;
there is no runtime consumer coverage.

The one next phase-scoped step is a coordinate-level source review of the full
machine-unreviewed candidate ledger, beginning with deterministic
declaration/definition/comment boundary dispositions and then reviewing the
remaining material candidates, including `getXPDF`. Do not begin architecture
comparison, prototype work, issue #10, or D2 until the D1D-A acceptance
conditions pass.
